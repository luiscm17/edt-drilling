A host read-only check found local service `MSSQL$EDM5000` running, as well as `LGC EDM Simultaneous Activity Monitor`; WellPlan PID 19120 had one established loopback TCP connection, but its remote port was not identified as a database port. These facts make a local SQL Server EDM instance plausible, **not proven as the active DSN**. A sampled Windows UI Automation tree had no exact `Database` or `Data Source` control label; it did have `Well Explorer`. No UI navigation, ODBC registration, SQL catalog or case contents were inspected. The selected database, record count and write targets remain unknown.

## Bounded ODBC and catalog readback

The user explicitly approved read-only inspection of the Windows ODBC registration, then authorized continued WellPlan investigation. The 32-bit and 64-bit system DSN entries named `EDM 5000.17 Single User Db` point through `sqlncli11.dll` to `localhost`'s `EDM5000` SQL Server instance and database `edm`. This is the sole EDM-named DSN observed in those ODBC registry views, **not proof** that the active WellPlan process selected it. REA's separate bounded process-module observation `ev_3c4f67e95ed8e6b0cd7bec4f0704f76585b6b867919638bf00b5060745063ebc` saw `odbc32.dll` and `sqlncli11.dll` loaded in WellPlan, consistent with that driver family but not a DSN binding.

A read-only Windows-integrated SQL connection to `localhost\EDM5000`, database `edm`, succeeded without using the credential supplied in chat. The catalog lists 2,239 tables; exact `COUNT_BIG(*)` queries returned `CD_CASE_T = 0`, `CD_WELLBORE_T = 1`, `DM_COMPANY_T = 0`. No rows, case identifiers or names were selected or retained. This **refutes an assumption that this database has no data**, but these three table counts neither establish the full database inventory nor prove the current WellPlan session uses this DSN. No SQL update, insert, delete, schema change, vendor UI action or login attempt was issued. SQL session metadata showed no program-name match for WellPlan at inspection time, which is inconclusive for an idle or brokered connection.

## Separate database provisioning feasibility

The user authorized provisioning a separate disposable EDM database/DSN **only after its procedure and destinations are verified**, without copying or modifying the existing database. Shipped Administration help (`EDM/Engineer_s_Desktop_Tools_WE.htm`) mentions an EDM Database Creation tool using editable SQL Server/Oracle scripts, but does not provide a validated invocation or prove that this installation contains a pristine compatible SQL Server schema/template. Under `C:\Landmark\EDT\EDM\Databases`, only the existing `edm.mdf` and `edm.ldf` were observed; no separate blank template was found in the bounded installed-tree filename search. REA classified `EDM/db_create.exe` as native PE (`ev_83eb6f66c9ad72437ab040a560e526455c21470cae6498a3df4d7594be42b4bb`); its resource inventory `ev_17b83522bcdfb527c89d3809f6f87e08c039a651bd905e3e7a9aea82b8a3c81d` exposed no embedded SQL script resource. REA inspected the managed `EDM/SQL Server Utility/SSUtils.exe` and found attach, detach, backup, restore and DSN-management entry points (`ev_b12e02296fa84df369c33570e77e7b47be041f9343e6f3c7c62cd20f617fc9fd`), but that is not evidence of a safe blank-schema creation workflow. **No isolated EDM database or DSN was created.** Provisioning remains blocked until a verifiable blank, version-compatible EDM schema/installer procedure and separate SQL data/log paths plus DSN-switch behavior are available. Running the installed utility against the current instance without that proof could alter or detach the populated EDM database.

## Isolation gate before a reference run

The user reports a newly installed application and a database-access prompt at launch. The inspected `edm` database has at least one wellbore row, but its origin (demo or user) and whether WellPlan currently selects this DSN are **not** verified. The credentials shared in conversation were not submitted, retained, or written to tools or artifacts. Do not infer that a newly installed database is disposable.

Before any case creation, calculation or save: identify the active EDM database and whether it contains existing records; establish a separate disposable database or equivalent reversible test workspace and writable profile/output paths; enumerate whether WellPlan can write outside this repository (database, logs, settings, license/profile). Confirm the synthetic case is isolated from user wells. If those controls cannot be demonstrated, stop at passive inspection and ask for a specific disposable environment. `research/wellplan-reference/` holds **our evidence only**; it does not sandbox the vendor process.
